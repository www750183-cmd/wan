# Koala Inspector 拆解报告 & 中文版对标设计

> 拆解对象：**Shopify Spy & Dropshipping - Koala Inspector**（koala-apps.io）
> 拆解日期：2026-09-22
> 说明：抓取该插件商店页正文的 `web_fetch` 运行时缺依赖，因此功能面来自检索摘要
> + 公开文档 + 同类实现对照。凡属推断的条目都标了「推断」，没有伪装成实测。

---

## 一、它到底卖的是什么

Koala Inspector 表面上是「店铺侦察工具」，但它真正的商品是**后端数据**，不是插件本身。

拆开看它只有两层：

| 层 | 内容 | 是否可本地复刻 |
|---|---|---|
| **采集层**（插件内） | 读当前页面的 `window.Shopify`、`script[src]`、`link[href]`、`meta`、Cookie 名，把结果发给后端 | ✅ 完全可复刻，代码量很小 |
| **数据层**（云端） | 应用/主题指纹库、店铺流量与销量数据、店铺索引、历史快照 | ❌ 拿不到，这是它的护城河 |

关键结论：**它的插件是一个采集器，价值在服务器上。** 所以「做一个同等功能的中文版」
这句话必须拆成两半回答：

- **能同等的**：主题识别、应用识别、像素识别、产品库、爆款榜、导出 —— 这些全靠公开信号，
  本地就能算，而且能做得更透明。
- **不能同等的**：真实销量/流量、跨店铺索引、历史变化追踪 —— 这些需要持续采集的数据资产，
  不是代码问题。本中文版用**可解释的启发式估算**替代，并明确标注为估算。

这一点必须先说清楚，否则「同等功能」就是空话。

## 二、功能面逐项拆解

| # | 功能 | 它的实现方式（拆解） | 中文版实现 | 能否同等 |
|---|---|---|---|---|
| 1 | Shopify 店铺判定 | `window.Shopify` + CDN 特征 + meta 标记 | `lib/injected.js` 多信号投票（≥3 分判定），**并展示投票明细** | ✅ |
| 2 | 主题名 / 主题商店 ID | `window.Shopify.theme` | 同上，另加 70+ 主题参考库映射厂商/免费付费/类型 | ✅ |
| 3 | 是否二次开发 | 云指纹识别 | 资产路径血缘推测（`/assets/dawn.*` 等） | ⚠️ 弱于它 |
| 4 | 已装应用识别 | 云端签名库匹配 | **本地 100+ 条指纹库**，命中附证据片段与置信度 | ✅ |
| 5 | 追踪像素识别 | 云端签名库 | **本地 22 条像素库**，按「广告像素/分析/营销自动化」分类 | ✅ |
| 6 | 产品库抓取 | `/products.json` 翻页 | 同样路径，支持最多 40 页 × 250 条 | ✅ |
| 7 | 爆款/选品榜 | 云端销量数据 + 排序 | 抓店铺自己的 `/collections/all?sort_by=best-selling` | ✅ **更硬**（见下） |
| 8 | 销量与营收估算 | 第三方流量数据合作方 | 启发式模型，**公式与输入全部外显** | ❌ 精度不等，但透明 |
| 9 | 流量估算（访问量） | 第三方流量数据 | 未做（无数据源，编不出来） | ❌ |
| 10 | 店铺收藏 / 历史 | 云端账号 | `chrome.storage.local` 本地保存 | ✅ 本地版 |
| 11 | CSV , | 云端生成 | 本地生成，带 UTF-8 BOM | ✅ |
| 12 | AliExpress 找同款 | 图片反查接口 | 未做（需要图像检索服务） | ❌ |
| 13 | 主题文件下载 | 云端抓取 | 未做（涉及批量拉取商家资产） | ❌ |
| 14 | 跨店铺对比 | 云端索引 | 已实现算法 `compareStores()`，UI 入口待接 | ⚠️ 部分 |

### 关于第 7 项：为什么「更硬」

Koala 这类工具的销量数字是**估算**，而 `/collections/all?sort_by=best-selling`
是 **Shopify 官方接口返回的、商家自己后台认可的销量排序**。它是事实，不是估算。

Koala 当然也能拿到这个排序，但它没说清自己的数字哪部分来自这里、哪部分来自流量估算。
本中文版把两者**严格分开**：爆款榜标为「店铺自认」，营收标为「估算」并给出置信度。

## 三、中文版的技术选型与取舍

### 3.1 零后端、零构建

参考实现选型对照：`tonic20/stackpeek-extension`（MIT）是同品类最接近的开源实现，
但它同样是**客户端采集 + 服务端签名库**架构（`lib/api.ts` 里 `postDetect()` 发到
`api.stackpeek.app`），fork 它等于只拿到采集器、拿不到核心资产。

因此本版选择**完全另起，纯原生 ES 模块 MV3**：

| 取舍 | 选择 | 理由 |
|---|---|---|
| 构建步骤 | **无** | 源码即可加载；没有 Vite/WXT 依赖，也就没有构建失败、版本漂移、lockfile 攻击面 |
| UI 框架 | 原生 DOM + 模板串 | 侧边栏只有 7 个视图，框架的收益小于它的体积与构建复杂度 |
| 指纹库位置 | **内置在扩展里** | 断网可用、可审计、可自己加规则；代价是更新指纹要发新版本 |
| 数据去向 | **不出本机** | 没有任何 `fetch` 指向第三方；`chrome.scripting` 只读当前标签页 |

### 3.2 权限最小化

只用 `activeTab` + `scripting`，不用 `<all_urls>`。
代价是必须由**用户点击工具栏图标**授予当前页面访问权，因此把「点图标 → 开面板 → 自动扫描」
做成一条龙主路径（`background.js` 的 `chrome.action.onClicked`）。

## 四、实测暴露并修掉的问题

拆解的价值一半在「它怎么做」，另一半在「照做会踩什么坑」。以下每条都是真实干跑或
真实浏览器端到端测试暴露的：

### 4.1 指纹误报（9 类）

| 误报 | 症状 | 修法 | 发现方式 |
|---|---|---|---|
| 主题血缘扫整页 HTML | 任何用 Tailwind 的店铺都被判成「基于 Flex 开发」（`flex-row` 命中） | 血缘匹配**只扫 script/link**，且要求「主题名 + 资源扩展名」 | 真实站点干跑 |
| `localization-form` 作为 Shopify Markets 指纹 | **每一个** Dawn 店铺都误报装了 Markets | 换成 `shopify-section-localization` | 代码审查 + 干跑 |
| `dataLayer` 作为 GTM 指纹 | GA4-only 店铺同时被报成装了 GTM | 从 GTM/GA4 的 globals 里移除 `dataLayer` | 代码审查 |
| `analytics.js` 作为 Segment 指纹 | 任意同名自建文件都误报 | 收紧为 `cdn.segment.com/analytics` | 代码审查 |
| `cky-` 作为 CookieYes 指纹 | **命中 CSS 变量 `--sticky-header-height`**（"sti\|cky-\|header"） | 改为 `cky-consent` / `cky-btn` / `cookieyes.com` | **浏览器端到端回填证据** |
| `zE(` 作为 Zendesk 指纹 | 命中压缩 JS 里的随机函数调用（`Object.freeze(w[L][y]),function(t,e,...`） | 删除，改用 `window.zE` 全局变量 + `zdassets.com` | **浏览器端到端回填证据** |
| `capi-` 作为服务端转化指纹 | **命中 `data-facebook-capi-enabled="false"`** —— 属性明说「未启用」 | 删除，改用 `conversions-api` | **浏览器端到端回填证据** |
| `aw-` / `ea-` / `om-` / `ae-` / `gem-` 等两字符前缀 | 在噪声页面上乱命中 | 全部删除，改用完整域名 | 代码审查 |
| `route.com` | 被 `reroute.com` 子串命中 | 加词边界 `\broute\.com` | 代码审查 |

**后三类是「每条命中都必须回填证据片段」这条设计的直接回报。**
只看「识别到 CookieYes」永远发现不了问题；把触发它的原文
（`--sticky-header-height`）摊在界面上，一眼就知道错了。

### 4.2 MV3 的 API 边界（Node 层完全测不出）

| 问题 | 现象 | 修法 |
|---|---|---|
| **SW 里没有 `URL.createObjectURL`** | 五种导出在真浏览器里全部报 `is not a function`，导出功能 100% 失效 | background 只生成内容，落盘交给侧边栏页面 |
| SW 不支持动态 `import()` | `import() is disallowed on ServiceWorkerGlobalScope` | 扩展本身用静态 import 已合规 |
| 无 `tabs` 权限时 `tab.url` 为 undefined | 面板在正常店铺页面上显示「当前页不支持扫描」，把用户引向错误方向 | 区分「拿不到 url」与「页面不支持」 |

这些问题单测和干跑都发现不了 —— **必须真把扩展加载进浏览器**。

### 4.3 Chrome 137+ 移除了 `--load-extension`

实测 Chrome 153 下，无论 headless 还是 headful，`--load-extension` 都不生效，
扩展不会出现在 target 列表里。**替代路径是 CDP 的 `Extensions.loadUnpacked`**，实测 Chrome 153 可用。
注意这限制的只是**命令行开关**：手动在 `chrome://extensions` 点「加载已解压的扩展程序」完全不受影响，
所以它只影响自动化测试，不影响用户安装。

以上全部固化为 `test/run-tests.mjs` 的**误报回归测试**与 `tools/verify.mjs` 的
**SW 侧 API 白名单**——误报比漏报危险，它会让人拿着假结论去下单。

## 五、追加：「店铺变化」功能的拆解与实现

### 6.1 原版到底是什么

读过 Koala 自己的文档后，这件事没有悬念：

> **Shop Tracking**：*"add a competitor and it **re-checks that store for you and logs what moved**,
> including apps added or removed, a theme swap, new or dropped products, price changes,
> and variant changes."*
>
> **Live Trends**：*"shows real-time sales activity across Shopify stores, including **which products
> were added recently** and **how current bestsellers compare to last month**."*

也就是说：**原版的「实时销量 / 最近订单」是变更检测，不是订单数据。**
它没有任何订单接口，护城河是**持续重扫同一批店铺攒下来的历史**。

这解释了它的产品结构为什么是「加一个竞品，我替你盯着」——数据是靠时间积累出来的，
不是靠某个神奇接口。而这一点，**零后端的本地扩展同样能做到**。

### 6.2 四条被实测排除的路（不做无用功）

| 候选数据源 | 实测结果 | 结论 |
|---|---|---|
| `/orders.json` | HTTP 404 | 需鉴权，不可用 |
| `variants[].inventory_quantity` | **0/238、0/419、0/2525 个变体带该字段** —— 三家店全部不暴露 | 库存反推销量不可行 |
| `variants[].updated_at` | 每家店**所有变体时间戳完全相同**（= 最后一次全量同步时间） | 批量刷新，零信息量 |
| `/collections/<h>/products.json?sort_by=X` | 三种排序返回**字节数完全相同**、前 3 个产品一致 | 该端点忽略 sort_by |
| `/checkouts.json`、`/recommendations/products.json` | HTTP 404 | 不可用 |

第二、三条特别值得记下来：它们看起来像是「能算出销量」的入口，实测证明是死路。
**只有测过才知道**——这也是为什么本轮所有结论都带实测数字。

### 6.3 中文版实现：四层证据

| 层 | 数据源 | 证据强度 | 是否需要历史 |
|---|---|---|---|
| **变动事件流** | 前后两次快照差分 | 强（售罄/补货/上架/下架/改价） | ✅ 需要 |
| **爆款榜位次变化** | 两次扫描的 best-selling 排名对比 | 中 | ✅ 需要 |
| **最近上架时间线** | 产品 `published_at` | 强 | ❌ 单次扫描即可 |
| **断货分析** | 当前 `availableVariants` / `variantCount` | 中 | ❌ 单次扫描即可 |
| **上新节奏曲线** | `published_at` 按月聚合 | 中 | ❌ 单次扫描即可 |
| 应用增减 / 主题更换 | 快照差分 | 参考 | ✅ 需要 |

关键设计：**首次扫描就有内容**（上架/断货/节奏/爆款榜），第二次起才出现变动事件。
界面上用「观测基线」卡片把这件事说清楚，而不是让用户以为功能坏了。

### 6.4 分级与降噪

- 事件按 `strong / medium / weak` 三档标注并在 UI 分组，避免把「应用增减」当成成交
- 价格波动 < 1% 视为噪声（汇率/四舍五入），不报
- 爆款榜排名：中段浮动 1 位不报（噪声），**但头部（前三）换位必须报**——那是销量反转
- 同一分钟内重复扫描覆盖而非追加，避免刷一下就把历史挤掉

### 6.5 一个真实的兼容性坑（以及诚实的降级）

实测 `kuura.co`：**所有 HTML 请求被 301 到 `kuura.myshopify.com`，而跨域 HTML 响应不带
`Access-Control-Allow-Origin`，浏览器直接拒绝。** 同页面的 `/products.json` 却能成功——
因为 Shopify 给 JSON 端点加了 CORS 头。

后果：这类店铺的 `best-selling` 排序**在页面上下文里根本读不到**。

因此实现为分层降级：

1. 先试 collection 页面 HTML → 拿到真实销量排序（绝大多数字典可用，实测 deathwishcoffee 拿到 24 名）
2. 失败则退到 `/collections/<h>/products.json` 取**合集成员**
3. **成员列表在 UI 上被明确标注「非销量排序」，与爆款榜分开成两块**，并给出精确到原因的诊断文案

这里最容易犯的错是把降级数据当主数据用。把「合集里有什么」说成「什么卖得好」，
比什么都不显示更糟。

### 6.6 与 Koala 的差距（仍然存在）

- Koala 可以**后台持续自动重扫**，用户不用手动点；本版靠用户每次扫描累积快照
  （每次扫描都存一份，最多保留 12 份，间隔建议隔天）
- Koala 有跨店铺索引，能横向比对同类目店铺的变动；本版只能看单店
- 这两项都是数据资产差距，不是代码差距

## 六、复刻边界（必须承认的部分）

1. **没有流量数据。** 月访问量、渠道占比这类数字需要第三方数据源，本地拿不到，因此不做。
2. **销量是估算。** 置信度在界面上明示，公式可反推，但它不是财报。
3. **指纹库是静态的。** 新上线的应用要手动加规则（`lib/signatures.js` 一条记录即可），
   它家的云端库可以热更新。
4. **反爬会挡住部分店铺。** 部分店铺的 `/products.json` 已关闭或有人机校验，
   此时产品库与选品不可用，但主题/应用/像素检测不受影响（这三项不需要发请求）。
5. **「店铺变化」需要时间积累。** 第一次扫描只有单次可得的内容；变动事件要靠
   隔一段时间再扫一次。Koala 的后台自动重扫是它的服务优势，本版不做后台常驻。
