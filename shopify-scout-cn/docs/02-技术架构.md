# 技术架构

## 一、为什么是零后端 + 零构建

参考实现 `tonic20/stackpeek-extension`（MIT）是同品类最接近的开源项目，但它的
`lib/api.ts` 里写着：

```ts
const base = import.meta.env.WXT_API_BASE ?? "http://localhost:3070";
const res = await fetch(base + "/api/v1/detect", { ... });
```

也就是说，它的指纹库在服务端。fork 它只能拿到采集器，拿不到核心资产——而采集器本身
只有几百行。同品类的 Koala Inspector 也是这个架构。

结论：**要做一个自持的中文版，指纹库必须自己写，因此架构上也没有必要引入后端。**

去掉后端之后，构建步骤的收益也随之消失：

| 项 | WXT/Vite 方案 | 本方案 |
|---|---|---|
| 依赖数 | 20+ 个 devDependency | **0** |
| 构建 | `wxt build` 产出 `.output/chrome-mv3` | **无**，源码即产物 |
| 加载 | 加载构建产物目录 | 加载源码目录 |
| 改一行代码 | 重新构建 + 刷新扩展 | 刷新扩展 |
| 失败模式 | 依赖版本漂移、lockfile 投毒、构建配置 | 无 |

侧边栏只有 7 个视图，原生 DOM + 模板字符串完全够用，框架带来的体积与构建复杂度不划算。

### 为什么采集必须在 MAIN world

`window.Shopify` 是页面 JS 运行时写在页面全局对象上的。内容脚本默认运行在 ISOLATED
world——同一个 DOM，但**独立的 JS 全局对象**，读不到它。所以必须用
`chrome.scripting.executeScript({ world: 'MAIN' })`。

（另一条路是往页面注入 `<script>` 标签，再用 `window.postMessage` 回传。
`world: 'MAIN'` 是 Chrome 111+ 的原生做法，更干净，本版走这条。）

### 注入函数的自包含约束（最容易踩的坑）

`executeScript` 序列化的**只有函数源码本身**，模块作用域的一切都不会跟着过去。
因此 `lib/injected.js` 里每个函数的辅助常量都必须声明在**函数体内**：

```js
// ✗ 页面里会 ReferenceError: PAGE_SIZE is not defined
const PAGE_SIZE = 250;
export async function collectCatalogue() { ...PAGE_SIZE... }

// ✓
export async function collectCatalogue(maxPages) {
  const PAGE_SIZE = 250;   // 必须在这里
  ...
}
```

`test/run-tests.mjs` 有一组用例专门守这条：它把注入函数的 `toString()` 拿出来，
断言其中不出现任何模块级标识符。这是 Stackpeek 注释里记录过的真实事故
（页面里抛 ReferenceError 被 catch 吞掉，表现为「所有店铺都读不到目录」）。

## 三、匹配引擎

### 证据面（6 个）

`matchApps` 不是在一整坨文本里搜关键词，而是把页面拆成 6 个**互相独立**的面，
命中的是哪个面会随结果一起返回，作为给用户看的证据：

| 面 | 来源 | 说明 |
|---|---|---|
| `script` | `<script src>` 完整 URL | 最强信号，第三方应用基本都在这里露头 |
| `link` | `<link href>` 完整 URL | 样式与预加载资源 |
| `inline` | 无 `src` 的 `<script>` 文本（截断 120KB） | 很多应用把配置写在内联脚本里 |
| `html` | `documentElement.outerHTML`（截断 400KB） | 兜底，能捞到 data 属性与 JSON 块 |
| `meta` | `<meta>` 的 name/content | Shopify 自身的标记 |
| `cookie` | **只有名字** | Cookie 值可能含购物车/会话令牌，绝不采集 |

另外 `window.globals` 单独处理：命中全局变量优先级最高，因为它证明**脚本真的执行过**，
而不是只被引用了一下（例如 Klaviyo 的 `window._learnq`）。

### 置信度分级

| 等级 | 含义 | 例子 |
|---|---|---|
| `high` | 特征专属于该应用 | `static.klaviyo.com`、`window.fbq` |
| `medium` | 较强，但同厂商多产品会共用 | `sendinblue.com`、`junip.co` |
| `low` | 弱信号，仅供参考 | `scarcity`、`low-stock` 这类通用词 |

### 误报防线（本项目最硬的工程约束）

误报比漏报危险得多：漏报只是少一条信息，误报会让人拿着假结论去下单。
干跑真实店铺时抓到并修掉的 6 类误报，全部固化为回归测试：

| 误报 | 根因 | 防线 |
|---|---|---|
| 任何 Tailwind 店铺都被判「基于 Flex 开发」 | 血缘匹配扫了整页 HTML，`flex-row` 命中 | 只扫 script/link，且要求「主题名 + 资源扩展名」 |
| 每个 Dawn 店铺都「装了 Shopify Markets」 | `localization-form` 是 Dawn 默认类名 | 换成 `shopify-section-localization` |
| GA4-only 店铺同时「装了 GTM」 | `dataLayer` 对两者都存在 | 从 GTM/GA4 的 globals 移除 `dataLayer` |
| 任意 `analytics.js` 都「是 Segment」 | 通用文件名被当指纹 | 收紧为 `cdn.segment.com/analytics` |
| `reroute.com` 被判「装了 Route」 | 子串匹配 | 加词边界 `\broute\.com` |
| 噪声页面上 `aw-`/`ea-`/`om-`/`ae-`/`gem-` 乱命中 | 两字符前缀 | 全部删除，改用完整域名 |

## 四、主题识别：三级信号

按可靠性从高到低：

**① `Shopify.theme.theme_store_id`（事实）**
非空 = 官方主题商店主题；为空 = 非商店直接安装。

**② `Shopify.theme.schema_name`（事实，且是最被低估的信号）**
这是主题 schema 的标识，**商家改主题名也改不掉它**。

实测 `deathwishcoffee.com`：

```js
Shopify.theme = {
  name: "Sept 10, 2026",        // 商家按日期命名
  id: 135654604855,
  schema_name: "Dawn",          // ← 底座血缘的铁证
  schema_version: "10.0.0",
  theme_store_id: null,
  role: "main"
}
```

只靠 `name` 只能得出「自定义主题」；加上 `schema_name` 就能确定地说
「基于 Dawn 二次开发」。Koala 那类工具在这一项上给的是模糊描述，本版给的是确定结论。

**③ 资产路径推测（推测）**
`/assets/dawn.min.js` 这类文件名能补充线索，但**只能作为线索展示**，
不能覆盖 ② 的结论，也绝不能扫整页 HTML。

## 五、营收估算模型的来历与边界

Koala Inspector 的销量/流量数字来自第三方流量数据合作方。本地拿不到，硬编一个
「精确」数字只会骗人。因此本版的做法是：**把不确定性显式化**。

```
规模评分（0–100）= Σ 归一化信号 × 权重
  产品数量 30 | SKU 总数 20 | 已装应用数 15 | 投放像素数 15
  近 30 天上新 10 | 折扣依赖度 −10

月订单量 ≈ 产品数^0.42 × 6 × 规模系数(0.4–1.6) × 上新系数(0.8–1.3)
客单价   ≈ 价格中位数 × 1.25
月营收   ≈ 月订单量 × 客单价

置信度：产品数 ≥60 且应用数 ≥5 → 中；再满足产品数 ≥200、应用数 ≥10、像素数 ≥2 → 中高
```

权重与指数都是经验值，写死在 `lib/estimate.js` 里，界面上逐项展开可见，**可以自己改**。
模型的定位是「横向比较店铺的量级」，不是财务测算。

作为对比，**爆款排名不经过任何模型**——它直接来自店铺自己的 `best-selling` 排序，
是事实。这个区别在界面上被刻意放大：爆款榜标「店铺自认」，营收标「估算」。

## 六、隐私设计

| 数据 | 处理 |
|---|---|
| 页面 URL | 只取 `origin`（scheme + host + port），path 只用于本地展示，不外发 |
| 同源资源 URL | 保留 path（部分指纹无 host，靠 path 匹配），剥掉 query 与 fragment |
| Cookie | **只取名字，不取值** |
| `rel=canonical/next/prev/alternate/shortlink/amphtml` | 一律不采集（会暴露「你在看哪一页」） |
| 全部扫描结果 | 只进 `chrome.storage.session`（关浏览器即清），历史/收藏进 `chrome.storage.local` |
| 出站请求 | **零**。扩展自身不发任何跨域请求；唯一网络行为是 `lib/injected.js` 里在页面同源下的 `/products.json` 等读取 |

## 七、店铺动态引擎（「店铺变化」）

### 数据流

```
每次扫描：
  scan() 结果
      │
      ├─ loadHistory(host)            ← chrome.storage.local['snapshots'][host]
      │     返回历史快照（旧 → 新，不含本次）
      │
      ├─ buildTimeline({result, history})
      │     ├─ makeSnapshot(result)          本次快照（紧凑三元组）
      │     ├─ diffSnapshots(prev, curr)     差分 → 事件流
      │     ├─ newProductCadence()           12 个月上新曲线（单次可得）
      │     ├─ recentProducts / soldOutNow / topSellers
      │     └─ return { snapshot, events, cadence, ... }
      │
      └─ saveSnapshot(host, timeline.snapshot) ← 落盘，供下次差分
```

**顺序不能反**：必须先把历史读出来，再算时间线，最后才写本次快照。
反了的话本次快照会被当成「上一次」，所有差分恒为零。

### 快照的紧凑化

`chrome.storage.local` 容量有限，而 3000 个产品 × 12 份快照会撑爆。因此快照里每个产品只存三元组：

```js
products: { [handle]: [price, availableVariants, variantCount] }
```

产品数上限 1500（按爆款排名优先保留），每店最多 12 份快照。
同一分钟内重复扫描**覆盖**而非追加 —— 否则用户连点几次「扫描」就把历史挤没了。

### 差分事件与证据强度

| 强度 | 事件 | 含义 |
|---|---|---|
| `strong` | `sold_out` / `restocked` / `new_product` / `delisted` / `price_drop` / `price_rise` | 两个时间点之间的**实际状态变化**，是观测事实 |
| `medium` | `part_sold_out` / `rank_up` / `rank_down` / `new_to_rank` | 相对变化，反映销量走势 |
| `weak` | `app_added` / `app_removed` / `theme_changed` | 运营动作，不是成交 |

强度分级不是为了好看：它让用户能一眼分清「这家店真的卖断货了」和「这家店加了个应用」。

### 降噪规则（都是实测调出来的）

| 规则 | 原因 |
|---|---|
| 价格波动 < 1% 不报 | 汇率换算与四舍五入会产生 0.5% 级别的假变动 |
| 爆款榜排名浮动 1 位不报 | 榜单中段的 1 位浮动是噪声 |
| **但头部（前三）换位必须报** | 第 2 名和第 1 名互换是实打实的销量反转 |
| 只报「全部售罄」与「恢复有货」两个翻转 | 中间状态变化太频繁，会淹没有效信号 |
| 小于 1% 的变体数变化不报 | 同上 |

### 首次扫描的可用性

差分需要历史，但产品不能让首次扫描的用户看到一片空白。因此单次即可得的
四类内容（最近上架、断货分析、上新节奏、当前爆款榜）始终渲染，
并在「观测基线」卡片里明确写出「这是首次扫描，隔一段时间再扫一次就会出现变动事件」。
**把「还没有历史」和「功能坏了」区分开**，是这类时间维度功能的关键体验点。

### 分层降级：爆款榜读不到怎么办

实测 `kuura.co` 暴露的兼容性坑：该店把所有 HTML 请求 301 到 `*.myshopify.com`，
而跨域 HTML 响应不带 `Access-Control-Allow-Origin` → 浏览器直接拒绝。
同页面的 `/products.json` 却能成功，因为 Shopify 给 JSON 端点带了 CORS 头。

于是 `collectCatalogue` 里的爆款榜抓取做成三层：

1. **HTML 优先**：`/collections/<handle>?sort_by=best-selling` → 真实销量排序
2. **JSON 降级**：`/collections/<handle>/products.json` → 合集成员（**该端点忽略 `sort_by`**，
   实测三种排序返回字节数完全相同）
3. **明确标注**：降级数据在 UI 上单独成块，标题写明「合集成员（非销量排序）」，
   并附上精确到原因的诊断文案

把「合集里有什么」说成「什么卖得好」，比什么都不显示更糟。这条在代码注释与 UI 里都写了。

## 八、验证策略（三层，缺一层就会漏真实缺陷）

| 层 | 手段 | 覆盖 | 抓不到什么 |
|---|---|---|---|
| 单元 | `node --test`，48 个用例 | 指纹库自检、匹配引擎、主题解析、估算、导出、误报回归 | 浏览器行为、API 是否存在 |
| 静态门禁 | `node tools/verify.mjs` | manifest 字段/引用完整性、无远程代码与 eval、本地 import 可解析、**SW 侧 API 白名单**、图标 PNG 结构与内容、**全部 JS 语法检查**、**BOM 检测**、UTF-8 编码 | 运行期才暴露的问题 |
| 集成干跑 | `node tools/dry-run.mjs <url>` | 用真实 HTML 跑通整条管线 | `chrome.*` API、权限、manifest |
| 端到端 | `node tools/browser-test.mjs <url> --host-perm` | 真浏览器加载扩展、UI 渲染、真实消息协议、MAIN world 注入、导出全链路 | 只有真人点击工具栏那一步 |

### 端到端测试是怎么做的

用 CDP 驱动浏览器，`--load-extension` 加载扩展，然后从**扩展自己的侧边栏页面**
发一条真实的 `chrome.runtime.sendMessage({action:'scan'})` —— 也就是用户实际会走的路径：

```
侧边栏页面 → sendMessage('scan') → background.js scan()
  → scripting.executeScript(MAIN world) → collectSignals
  → matchApps / matchPixels / resolveTheme / estimate → 返回结果
```

分三个阶段执行，每阶段独立 eval，这样某阶段卡住不会丢掉前面已拿到的结果。

**为什么不用 Service Worker 上下文直接跑**：HTML 规范禁止在 ServiceWorkerGlobalScope
使用动态 `import()`（w3c/ServiceWorker#1356）。扩展自己用静态 import 不受影响，
但测试脚本没法从 SW 里动态加载模块。走侧边栏页面反而更接近真实路径。

**浏览器选择（Chrome 优先）**：Chrome 137 起移除了 `--load-extension` 命令行开关，
实测 Chrome 153 下该开关完全无效。但 Chrome 提供了替代路径 —— **CDP 的
`Extensions.loadUnpacked`**，实测可用（返回扩展 ID 并正常注册 Service Worker）。
脚本因此**默认用 Chrome**，Edge 作为兜底（它仍支持旧开关）。

> 关键区分：被移除的是**命令行开关**，不是「加载未打包扩展」这个能力本身。
> 手动在 `chrome://extensions` 点「加载已解压的扩展程序」完全不受影响 ——
> 这个限制只影响自动化，不影响用户安装。

`--host-perm` 模式会在临时副本的 manifest 里补上目标站点的 host 权限 —— 因为
`activeTab` 必须由真人点击工具栏授予，自动化给不了。这个差异在输出里明确标注，不混进结论。

### 端到端测试抓到的三个 Node 层看不见的问题

| 问题 | 现象 | 修法 |
|---|---|---|
| **MV3 Service Worker 里没有 `URL.createObjectURL`** | 五种导出全部报 `is not a function`——导出功能在生产环境 100% 失败 | background 只生成内容，落盘改在侧边栏页面做（`panel.js` 的 `doExport`） |
| **SW 不支持动态 `import()`** | `import() is disallowed on ServiceWorkerGlobalScope` | 扩展本身用静态 import 已合规；这条只影响测试写法 |
| **无 `tabs` 权限时 `tab.url` 是 undefined** | 面板在正常店铺页面上显示「当前页不支持扫描」，把用户引向错误排查方向 | 把「拿不到 url」与「页面不支持」区分开，改为提示「点工具栏图标可自动扫描」 |

  并附中文指引「请点击工具栏上的扩展图标重新扫描」—— 证明 activeTab 设计按预期工作，
  错误信息也指对了方向

### 一次自己造成的事故（已固化为门禁）

用 PowerShell 的 `Get-Content -Raw` / `Set-Content -Encoding utf8` 备份还原
`background.js` 做反证测试时，中文经 ANSI 码页往返变成乱码，一个字符串字面量被截断
→ 整个 Service Worker 注册失败 → 扩展在浏览器里根本不加载。

当时门禁**全绿**，因为乱码本身是合法 UTF-8，编码自检查不出来。事后补了两道门禁：

1. **全部 JS 语法检查**（`node --check`，覆盖 `tools/` 与 `test/`，不只扩展本体）
2. **BOM 检测** —— 无 BOM 的文件被 `Set-Content -Encoding utf8` 覆写后必然带 BOM，
   这是该事故的直接指纹

教训：**不要用 shell 做文本文件的读写往返**，尤其是有非 ASCII 内容的文件。
要改文件就用带编码保证的工具，改完立刻跑语法检查。

### 干跑器的诚实标注

干跑器刻意不复用 `lib/injected.js`（浏览器 API 写的，Node 里跑不了），而是用正则从 HTML
还原同样的 signals 结构。它有自己的标注：拿不到主题名时写明「干跑无法判定，不代表扩展失效」，
采不到 `script[src]` 时标注「该店铺疑似 JS 渲染，不计入指纹库评价」—— 避免把工具的限制
误读成产品的缺陷。

已知失败样本：`taylorstitch.com` / `mvmt.com` / `colourpop.com` 在本机网络环境下
fetch 失败（`fetch failed`，疑似 TLS 或区域限制），未纳入统计。
